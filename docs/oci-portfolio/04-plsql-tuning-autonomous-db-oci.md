# Project 4 — PL/SQL Performance Tuning on Autonomous Database (OCI)

Take a deliberately slow batch ETL on **Autonomous Data Warehouse**, diagnose bottlenecks with Oracle performance tools, and optimize through SQL/PL/SQL rewrites, indexing, partitioning, and materialized views.

## Skills demonstrated

- PL/SQL bulk processing (`BULK COLLECT`, `FORALL`)
- SQL tuning on **Autonomous DB** (execution plans, SQL Monitor)
- Partitioning and indexing strategy
- Before/after performance benchmarking
- Using **Database Actions** Performance Hub

## OCI services used

| Service | Role |
|---------|------|
| PORTFOLIO_ADW | Tuning target (batch runs here) |
| SQL Developer Web / Performance Hub | Diagnostics |
| Optional: PORTFOLIO_ATP | Source data generator |

## Prerequisites

- [00-shared-oci-setup.md](./00-shared-oci-setup.md)

## Phase 1 — Create the slow workload (Day 1)

### Step 1.1 — Create tuning lab schema

On **PORTFOLIO_ADW** as `ADMIN`:

```sql
CREATE USER tuning_lab IDENTIFIED BY "TuningLab#2026Lab"
  DEFAULT TABLESPACE DATA QUOTA UNLIMITED ON DATA;
GRANT CREATE SESSION, CREATE TABLE, CREATE VIEW, CREATE PROCEDURE TO tuning_lab;
```

### Step 1.2 — Create large fact table (unpartitioned)

```sql
CREATE TABLE tuning_lab.sales_txn (
    txn_id        NUMBER GENERATED BY DEFAULT AS IDENTITY,
    order_date    DATE NOT NULL,
    customer_id   NUMBER NOT NULL,
    product_id    VARCHAR2(32) NOT NULL,
    quantity      NUMBER(10),
    unit_price    NUMBER(12,2),
    revenue       NUMBER(14,2)
);

CREATE TABLE tuning_lab.dim_customer (
    customer_id   NUMBER PRIMARY KEY,
    region        VARCHAR2(50)
);

CREATE TABLE tuning_lab.dim_product (
    product_id    VARCHAR2(32) PRIMARY KEY,
    category      VARCHAR2(100)
);
```

### Step 1.3 — Generate volume (1M rows)

```sql
-- Customers: 10K
INSERT INTO tuning_lab.dim_customer
SELECT LEVEL, CASE MOD(LEVEL,5) WHEN 0 THEN 'South' WHEN 1 THEN 'North' WHEN 2 THEN 'East' WHEN 3 THEN 'West' ELSE 'Central' END
FROM dual CONNECT BY LEVEL <= 10000;
COMMIT;

-- Products: 1K
INSERT INTO tuning_lab.dim_product
SELECT 'P' || LEVEL, CASE MOD(LEVEL,4) WHEN 0 THEN 'Electronics' WHEN 1 THEN 'Office' WHEN 2 THEN 'Home' ELSE 'Sports' END
FROM dual CONNECT BY LEVEL <= 1000;
COMMIT;

-- Sales: 1M rows (batched)
BEGIN
  FOR batch IN 1..20 LOOP
    INSERT INTO tuning_lab.sales_txn (order_date, customer_id, product_id, quantity, unit_price, revenue)
    SELECT DATE '2024-01-01' + MOD(LEVEL, 730),
           MOD(LEVEL, 10000) + 1,
           'P' || MOD(LEVEL, 1000) + 1,
           MOD(LEVEL, 5) + 1,
           ROUND(DBMS_RANDOM.VALUE(10, 500), 2),
           0
    FROM dual CONNECT BY LEVEL <= 50000;
    COMMIT;
  END LOOP;
END;
/

UPDATE tuning_lab.sales_txn SET revenue = quantity * unit_price;
COMMIT;

EXEC DBMS_STATS.GATHER_TABLE_STATS('TUNING_LAB', 'SALES_TXN');
```

### Step 1.4 — Create intentionally bad PL/SQL procedure

```sql
CREATE OR REPLACE PROCEDURE tuning_lab.sp_load_daily_summary_slow (
    p_run_date IN DATE
) AS
    v_category   VARCHAR2(100);
    v_revenue    NUMBER;
    v_cnt        NUMBER := 0;
BEGIN
    DELETE FROM tuning_lab.daily_summary WHERE summary_date = p_run_date;

    FOR rec IN (
        SELECT txn_id, order_date, customer_id, product_id, quantity, unit_price
        FROM tuning_lab.sales_txn
        WHERE TO_CHAR(order_date, 'YYYY-MM-DD') = TO_CHAR(p_run_date, 'YYYY-MM-DD')  -- non-sargable
    ) LOOP
        SELECT category INTO v_category
        FROM tuning_lab.dim_product
        WHERE product_id = rec.product_id;  -- row-by-row lookup

        SELECT revenue INTO v_revenue
        FROM tuning_lab.sales_txn
        WHERE txn_id = rec.txn_id;

        INSERT INTO tuning_lab.daily_summary (summary_date, category, revenue, txn_count)
        VALUES (p_run_date, v_category, v_revenue, 1);
        v_cnt := v_cnt + 1;

        IF MOD(v_cnt, 100) = 0 THEN
            COMMIT;  -- too frequent commits
        END IF;
    END LOOP;
    COMMIT;
END;
/

CREATE TABLE tuning_lab.daily_summary (
    summary_date  DATE,
    category      VARCHAR2(100),
    revenue       NUMBER,
    txn_count     NUMBER
);
```

## Phase 2 — Capture baseline metrics (Day 1)

### Step 2.1 — Create benchmark log table

```sql
CREATE TABLE tuning_lab.benchmark_log (
    run_id        NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version_label VARCHAR2(50),
    started_at    TIMESTAMP,
    ended_at      TIMESTAMP,
    elapsed_sec   NUMBER,
    rows_processed NUMBER,
    notes         VARCHAR2(4000)
);
```

### Step 2.2 — Run slow procedure for one busy day

```sql
DECLARE
  v_start TIMESTAMP := SYSTIMESTAMP;
  v_run_id NUMBER;
BEGIN
  INSERT INTO tuning_lab.benchmark_log (version_label, started_at, notes)
  VALUES ('SLOW_V1', v_start, 'Row-by-row PL/SQL')
  RETURNING run_id INTO v_run_id;

  tuning_lab.sp_load_daily_summary_slow(DATE '2024-06-15');

  UPDATE tuning_lab.benchmark_log
  SET ended_at = SYSTIMESTAMP,
      elapsed_sec = EXTRACT(SECOND FROM (SYSTIMESTAMP - v_start))
                    + EXTRACT(MINUTE FROM (SYSTIMESTAMP - v_start)) * 60
                    + EXTRACT(HOUR FROM (SYSTIMESTAMP - v_start)) * 3600,
      rows_processed = (SELECT COUNT(*) FROM tuning_lab.daily_summary WHERE summary_date = DATE '2024-06-15')
  WHERE run_id = v_run_id;
  COMMIT;
END;
/
```

> For a 1M-row table with one day of data (~1,400 rows), slow proc may take minutes. Scale `sales_txn` to 10M if you want dramatic timings.

## Phase 3 — Optimization layer 1 — SQL rewrite (Day 2)

### Step 3.1 — Set-based replacement procedure

```sql
CREATE OR REPLACE PROCEDURE tuning_lab.sp_load_daily_summary_fast_v2 (
    p_run_date IN DATE
) AS
BEGIN
    DELETE FROM tuning_lab.daily_summary WHERE summary_date = p_run_date;

    INSERT INTO tuning_lab.daily_summary (summary_date, category, revenue, txn_count)
    SELECT p_run_date,
           p.category,
           SUM(s.revenue),
           COUNT(*)
    FROM tuning_lab.sales_txn s
    JOIN tuning_lab.dim_product p ON p.product_id = s.product_id
    WHERE s.order_date = p_run_date   -- sargable predicate
    GROUP BY p.category;

    COMMIT;
END;
/
```

## Phase 4 — Optimization layer 2 — PL/SQL bulk (Day 2)

If business logic requires procedural steps:

```sql
CREATE OR REPLACE PROCEDURE tuning_lab.sp_load_daily_summary_fast_v3 (
    p_run_date IN DATE
) AS
    TYPE t_rec IS RECORD (
        category VARCHAR2(100),
        revenue  NUMBER,
        txn_cnt  NUMBER
    );
    TYPE t_tab IS TABLE OF t_rec;
    l_data t_tab;

    CURSOR c_agg IS
        SELECT p.category, SUM(s.revenue), COUNT(*)
        FROM tuning_lab.sales_txn s
        JOIN tuning_lab.dim_product p ON p.product_id = s.product_id
        WHERE s.order_date = p_run_date
        GROUP BY p.category;
BEGIN
    DELETE FROM tuning_lab.daily_summary WHERE summary_date = p_run_date;

    OPEN c_agg;
    FETCH c_agg BULK COLLECT INTO l_data LIMIT 1000;
    CLOSE c_agg;

    FORALL i IN 1..l_data.COUNT
        INSERT INTO tuning_lab.daily_summary (summary_date, category, revenue, txn_count)
        VALUES (p_run_date, l_data(i).category, l_data(i).revenue, l_data(i).txn_cnt);

    COMMIT;
END;
/
```

## Phase 5 — Optimization layer 3 — Physical design (Day 3)

### Step 5.1 — Add indexes

```sql
CREATE INDEX tuning_lab.ix_sales_txn_date ON tuning_lab.sales_txn(order_date);
CREATE INDEX tuning_lab.ix_sales_txn_prod ON tuning_lab.sales_txn(product_id);
```

### Step 5.2 — Partition sales_txn by month

Autonomous DB supports partitioning. Migrate data:

```sql
CREATE TABLE tuning_lab.sales_txn_part
PARTITION BY RANGE (order_date) (
    PARTITION p2024_01 VALUES LESS THAN (DATE '2024-02-01'),
    PARTITION p2024_02 VALUES LESS THAN (DATE '2024-03-01'),
    -- ... add partitions per month or use INTERVAL
    PARTITION pmax VALUES LESS THAN (MAXVALUE)
)
AS SELECT * FROM tuning_lab.sales_txn;

ALTER TABLE tuning_lab.sales_txn RENAME TO sales_txn_old;
ALTER TABLE tuning_lab.sales_txn_part RENAME TO sales_txn;

EXEC DBMS_STATS.GATHER_TABLE_STATS('TUNING_LAB', 'SALES_TXN');
```

Re-run `FAST_V2` and confirm **partition pruning** in execution plan (`Pstart`, `Pstop` in plan output).

### Step 5.3 — Materialized view for repeated aggregates

```sql
CREATE MATERIALIZED VIEW tuning_lab.mv_category_daily
BUILD IMMEDIATE
REFRESH COMPLETE ON DEMAND
AS
SELECT s.order_date,
       p.category,
       SUM(s.revenue) AS revenue,
       COUNT(*) AS txn_count
FROM tuning_lab.sales_txn s
JOIN tuning_lab.dim_product p ON p.product_id = s.product_id
GROUP BY s.order_date, p.category;

CREATE INDEX tuning_lab.ix_mv_cat_daily ON tuning_lab.mv_category_daily(order_date, category);
```

Load procedure becomes:

```sql
INSERT INTO tuning_lab.daily_summary
SELECT order_date, category, revenue, txn_count
FROM tuning_lab.mv_category_daily
WHERE order_date = p_run_date;
```
